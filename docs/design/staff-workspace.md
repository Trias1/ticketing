# Staff workspace redesign

Status: approved and implemented 2026-10-08.

## Goal

Turn the staff side into a project workspace that combines:

- **Issue tracking** (numbered issues, labels per project, members, comments, activity, open/closed)
- **Notion-style navigation** (project switcher, starred projects, one dataset with several views, side peek)
- **Trello-style board** (cards with label chips, due badges, checklist progress, quick add)

It must not look like a copy of any existing product: own teal identity (`#0f766e`), zinc neutrals, own copy.

## Access model

- Access is **per project membership**, not per team. A project still belongs to a team (Cloud, DevOps, PM) for grouping.
- Roles: `owner` (manage members, labels, board columns, rename/delete project) and `member` (view, create/edit issues, comment, close/reopen).
- The creator of a project becomes its owner.
- Admins manage people and security only; they don't work on issues. They can see and change a user's project memberships from the Users page.
- The old PM cross-team `access` flag is replaced by memberships.
- Migration: every existing staff user becomes a member of every existing project in their team; the project creator becomes owner.

## Data model changes (additive)

| Change | Purpose |
| --- | --- |
| `projects.color`, `projects.icon` | Project identity in the switcher and header |
| `projects.issue_counter` | Allocates per-project issue numbers atomically |
| `tickets.number` + unique `(project_id, number)` | `#82` style references and `/issues/82` URLs |
| `tickets.closed_at`, `tickets.closed_by` | Real open/closed state |
| `project_members (project_id, user_id, role, starred)` | Membership, roles, starred projects |
| `project_labels (id, project_id, name, color, description)` | Labels defined per project (e.g. JAH, TBS, TKP) |
| `activity (project_id, ticket_id, actor_id, type, data)` | Issue history shown with comments |

`tickets.labels` keeps storing label references, now project label IDs. `ticket_replies` (already in the schema, unused) stores comments.

## Navigation

Sidebar (staff):

1. Project switcher (grouped by team, search, new project, view all)
2. Jump to… (Ctrl+K)
3. Your work: Dashboard, My issues, Projects
4. Starred projects
5. Current project: Issues, Activity, Members, Labels, Settings

## Issues

One page with three views sharing filters (label, assignee, search, sort) and state tabs (Open / Closed / All):

- **List**: number, title, labels, status column, checklist progress, due date, assignee, comment count, updated time
- **Board**: columns are the project's statuses; drag to move; quick add per column
- **Calendar**: issues placed on their due date

Clicking an issue opens a side peek (`?issue=82`); "Open full page" goes to `/issues/82`.

Checklists are Markdown task lists in the description (`- [ ] item`); progress is computed, and boxes can be toggled from the peek.

## URLs

- `/dashboard/{team}` — personal dashboard
- `/dashboard/{team}/issues` — my issues across projects
- `/dashboard/{team}/project` — my projects
- `/dashboard/{team}/project/{slug}/issues[?view=board|calendar&issue=82]`
- `/dashboard/{team}/project/{slug}/issues/new`, `/issues/{number}`
- `/dashboard/{team}/project/{slug}/activity|members|labels|settings`
- Old `/tiket/...` URLs redirect to the new ones.

## Running the 0018 migration

This database is managed with `drizzle-kit push`, not `drizzle-kit migrate` (`drizzle.__drizzle_migrations` is empty), so migration files are applied by hand.

Migration 0018 has two parts that must run together, in this order, in one transaction:

1. `drizzle/0018_staff_workspace.sql` — schema changes (generated by drizzle-kit).
2. `drizzle/0018_staff_workspace_backfill.sql` — data: issue numbers for existing tickets, project members (staff of the project's team; creator becomes owner), default labels per project, and conversion of old label values to label ids.

Production (Neon) already ran both on 2026-10-08, with a JSON backup taken first in `../_backup/db-2026-10-08T07-38-29-399Z/`.

Before running on another database with existing tickets, check the old label values first:

```sql
SELECT DISTINCT unnest(labels) FROM tickets;
```

The backfill maps only the 14 built-in label values (bug, feature, infra, ...). Any other value is dropped from the ticket, so add it to the mapping in the backfill first.
